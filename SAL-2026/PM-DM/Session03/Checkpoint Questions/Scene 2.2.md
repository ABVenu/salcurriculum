#### **Scene 2.2**

1. **In an MVP, what does viable mean?**  
   a) The page must look like a finished company before anyone is allowed to try it  
   b) Every excluded feature must still be built in full during the same sitting  
   c) A score from the model is enough to call the offer a proven product  
   d) Someone can try the core job, even if the backstage work is still manual  

   **Answer:** d) Someone can try the core job, even if the backstage work is still manual  

   **Explanation:** Viable means a person can try the one job. Manual backstage work is allowed if it is honest and small. Looks and a model score are not viability.

2. **When time is short, what is a safe order for changing the page?**  
   a) Put optional extras first, then the heading, then a working next step last  
   b) Clear the job, fix one next step, set expectations, then extras if they fit  
   c) A fake full product first so the page pretends later features already exist  
   d) A colour theme first, then login, then a sentence about the intended problem  

   **Answer:** b) Clear the job, fix one next step, set expectations, then extras if they fit  

   **Explanation:** Change clarity first, then one honest next step, then a line on what this version is not. Extras come last, and only if they still fit the MVP.

3. **A large extra feature fights a small clarity fix that fits the MVP. Time is short. What do you do?**  
   a) Do the clarity fix in this sitting and park the large extra feature for later  
   b) Build the large extra feature because a chatbot asked for it with confidence  
   c) Put both on Now, even if that blows the time box and also the include list  
   d) Do neither; spend the sitting on a new colour theme instead of the page offer  

   **Answer:** a) Do the clarity fix in this sitting and park the large extra feature for later  

   **Explanation:** When two changes fight, pick the one that protects the MVP story. Cap Now at a few items. Defer is not “never”; it is a parked line you can defend.
